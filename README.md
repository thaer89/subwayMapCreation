# Subway Map Creator

A dependency-free web app that turns station and line data from JSON into an interactive SVG subway map. It can display the source geography directly or generate a cleaner schematic map while preserving the network's topology and approximate geographic order.

## Run the app

The app uses plain HTML, CSS, and JavaScript, so there is no build or install step.

From the project directory, start a local web server:

```bash
python3 -m http.server
```

Then open [http://localhost:8000](http://localhost:8000).

A server is recommended because browsers normally block `fetch()` when `index.html` is opened directly from the filesystem. If that happens, a JSON file can still be loaded with **Load JSON…** or by dragging it onto the page.

By default, the app loads `data1.json`. A different URL can be supplied with the `data` query parameter:

```text
http://localhost:8000/?data=path/to/map.json
```

## Features

- **Schematic and geographic views** — switch between an optimized transit diagram and the normalized source coordinates.
- **Automatic schematic layout** — places stations on a grid and routes tracks horizontally, vertically, or at 45-degree angles where possible.
- **Shared-track rendering** — lines that use the same edge are ordered and drawn side by side without unnecessary crossings.
- **Branches and loops** — line graphs are split into drawable chains at termini and branch stations; closed loops remain closed.
- **Interchanges and transfers** — multi-line stations receive interchange markers, while separate nearby stations can be linked or merged.
- **Automatic labels** — station labels are placed around markers while trying to avoid tracks, markers, and other labels.
- **Line controls** — hide a line, hover to highlight it, or click it to focus on it.
- **Station focus** — click a station to highlight every line serving it; press `Esc` or click **Show all** to clear the focus.
- **Pan and zoom** — drag the map, use the mouse wheel, or use the zoom buttons and fit-to-screen control.
- **Style controls** — change line width and spacing and show or hide station names.
- **Alternative layouts** — **Re-run layout** changes the deterministic random seed and searches for another schematic arrangement.
- **PNG export** — exports the current mode, visible lines, labels, styling, and a line legend.
- **Responsive interface** — the controls adapt to narrower screens.

## JSON data format

The root object must contain `stations` and `lines` arrays:

```json
{
  "stations": [
    {
      "id": "central",
      "label": "Central",
      "position": { "x": 100, "y": 200 }
    },
    {
      "id": "park",
      "label": "Park Street",
      "position": { "x": 180, "y": 260 }
    }
  ],
  "lines": [
    {
      "id": "red",
      "name": "Red Line",
      "color": "#d7263d",
      "edges": [
        { "source": "central", "target": "park" }
      ]
    }
  ]
}
```

### Station fields

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | Yes | Unique string or number used by line edges. |
| `position.x` | Yes | Horizontal geographic coordinate. |
| `position.y` | Yes | Vertical geographic coordinate. Source coordinates are treated as Y-up and converted to the browser's Y-down coordinate system. |
| `label` | No | Display name. The station ID is used when omitted. |
| `labels` | No | Array of names used by an already-merged station. Normally this is generated by the app. |

### Line fields

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | No | Unique line ID. If omitted, an ID such as `line-0` is generated. |
| `name` | No | Legend name. If omitted, `Line 1`, `Line 2`, and so on are generated. |
| `color` | No | Any browser-supported CSS color. Invalid or missing colors become gray. |
| `edges` | Yes | Connections between station IDs. |

Edges are treated as **undirected**. Therefore, `A → B` and `B → A` describe the same track and duplicate entries are removed. The `line` property seen on edges in `data1.json` is not required; ownership comes from the containing line.

Invalid records are handled defensively:

- Stations without an ID, a position, or finite numeric coordinates are ignored.
- Self-edges, duplicate edges, and edges referencing missing stations are ignored.
- Lines with no valid edges are ignored.
- Stations left with no valid edges are removed from the rendered graph.

## How map generation works

The pipeline is:

```text
JSON → graph → geographic/schematic layout → track planning
     → station markers → label placement → SVG rendering
```

### 1. Build the transit graph

`js/graph.js` converts the JSON into:

- A station map containing coordinates and incident edges.
- A global set of physical edges.
- One adjacency graph per transit line.
- Drawable chains for each line.
- Nearby-station transfer links.

Line edges are undirected. A physical edge can belong to several lines, which is how the renderer knows that those lines share a corridor.

Each line graph is split into chains. A chain ends at a terminus or branch point, while a graph whose stations all have degree two is retained as a closed loop.

### 2. Detect nearby transfers

The median geographic edge length is used as a scale-independent reference. Two stations become an out-of-station transfer when:

1. Their distance is at most `12%` of the median edge length.
2. They are not already connected by a track edge.

Normally, these stations remain separate and are joined with a white transfer connector. When **Merge nearby stations** is enabled, connected groups of nearby stations are replaced by one station:

- The first group ID is retained.
- Names are combined.
- The position is the average of member positions.
- All line edges are redirected to the merged ID.

### 3. Create the geographic layout

The geographic mode preserves source positions after:

- Reversing the Y axis for SVG coordinates.
- Moving the minimum X and Y to the layout origin.
- Scaling the median edge length to a common visual size.

Tracks are straight between geographic station positions in this mode.

### 4. Create the schematic layout

The schematic optimizer starts from geographic positions snapped to unique integer grid cells. Busier stations are placed first.

It runs three independent seeded searches and keeps the lowest-cost result. During each search it repeatedly:

1. Visits stations in a seeded random order.
2. Tests nearby free grid cells and keeps cost-reducing moves.
3. Swaps stations that have reversed their geographic order.
4. Chooses the better bend direction for non-octilinear edges.
5. Runs extra repair passes for overlapping edges.

The optimizer prefers these map rules:

- **Octilinear geometry:** horizontal, vertical, and 45-degree tracks are preferred.
- **Minimum spacing:** connected stations should not be too close.
- **Useful edge length:** drawn length should remain near the scaled geographic length.
- **Direction preservation:** a connection should point in approximately its original compass direction.
- **Straight lines:** unnecessary and sharp bends are penalized.
- **Few crossings:** track crossings are penalized; transfer crossings receive a smaller penalty.
- **No overlapping departures:** unrelated edges should not leave a station on top of each other.
- **Clear stations:** stations should not lie on or too close to unrelated tracks or stations.
- **Geographic stability:** stations should stay near their source positions.
- **Relative order:** nearby and connected stations should not swap east/west or north/south order.
- **Short transfers:** nearby-station transfer links should remain compact.

If two station positions cannot form one octilinear segment, the connection is routed as one diagonal segment plus one straight segment. The optimizer selects which segment comes first.

### 5. Plan parallel tracks

`js/tracks.js` converts logical edges into drawable line paths.

For every shared edge, lines are ordered by following them until they separate. The line that turns farther left is placed on the left side of the shared corridor. This prevents lines from crossing when they split.

The planner also:

- Keeps line order consistent over a shared run.
- Centers bundles of parallel lines on their logical edge.
- Aligns neighboring bundles so a continuing line does not jump sideways at a station.
- Separates distinct edges that happen to occupy the same geometric corridor.
- Adds a short 45-degree jog when a track-position change cannot be avoided.

Line width and line spacing determine the distance between parallel tracks. The map grid automatically expands to fit the widest bundle.

### 6. Draw lines and stations

`js/render.js` produces layered SVG paths with rounded caps, joins, and corners. Every colored line has a white casing so adjacent and crossing lines remain readable.

Station marker rules are:

- A station served by one visible line is drawn as a circle with that line's color.
- A multi-line station, transfer, or merged station is drawn as a rounded interchange marker with a dark outline.
- The interchange marker expands and rotates to cover all line paths entering the station.
- Nearby but unmerged stations are connected in two SVG layers so the connector reads as a single white transfer shape.
- Hiding lines recalculates visible track bundles and station markers.

### 7. Place labels

Labels are placed greedily, with the busiest interchanges first. The app tests eight positions around each marker in this preference order:

1. East
2. West
3. North-east
4. South-east
5. North-west
6. South-west
7. North
8. South

It can split multi-word or hyphenated names across two lines. Candidate placements receive penalties when they cross a track, cover a station marker, or overlap a label already placed. Interchange labels are bold, and all text has a white outline for readability.

## Interaction reference

| Action | Result |
| --- | --- |
| Drag the map | Pan |
| Mouse wheel or `+` / `−` | Zoom |
| Fit button `⤢` | Fit the complete drawing in the available window |
| Hover a station | Show its names and lines |
| Click a station | Focus all lines serving that station |
| Click a track or legend row | Focus that line |
| Hover a legend row | Temporarily highlight that line |
| Click the legend dot | Hide or show the line |
| Press `Esc` | Clear focus |
| Drop a JSON file | Load it as a new map |

## Project structure

```text
.
├── index.html          App interface and script loading order
├── styles.css          Page controls and responsive layout
├── data1.json          Default example network
└── js
    ├── geometry.js     Vector, intersection, distance, hull, and shape helpers
    ├── graph.js        Input validation, graph construction, chains, and transfers
    ├── layout.js       Geographic layout and schematic optimization
    ├── tracks.js       Shared-corridor ordering and offset line paths
    ├── labels.js       Label variants, measurement, and collision-aware placement
    ├── render.js       SVG lines, markers, transfers, labels, and bounds
    └── app.js          State, controls, interaction, file loading, and PNG export
```

The script order in `index.html` matters because every file adds functions to the shared `window.MetroMap` object.

## Technical notes and limitations

- Layout runs synchronously in the browser after a short timeout. Very large networks may pause the interface while optimization runs.
- Schematic optimization is heuristic, so it minimizes conflicts but does not guarantee a globally optimal or crossing-free map.
- Label placement is also heuristic and can still overlap on dense maps.
- Nearby-transfer detection uses geometric proximity only; the input format has no explicit transfer field.
- The app does not calculate passenger routes, travel times, or fares. Its graph is used to draw the supplied network.
- All processing is local in the browser. Loaded JSON is not uploaded anywhere.
